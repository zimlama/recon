# Postmortem — zimlama/recon v0.2.1 release

> **Status:** Resolved.
> **Released:** 2026-10-14 (tag `v0.2.1`).
> **Affected versions:** `v0.2.0` install on small VMs (≤10 GB disk) behind MikroTik-class firewalls.
> **Severity:** `install.sh` could not complete end-to-end on this host class. Existing v0.2.0 deployments continued to work.
> **Reproducer host:** armubuntu VM (aarch64, 5 GB disk, 2.6 GB tmpfs, behind MikroTik 192.168.88.2). Verified `{"status":"ok","version":"0.2.1"}` on `http://localhost:8000/health`.
> **Commits since v0.2.0:** 9 — `2789bae`, `78e1776`, `514ad72`, `f0d0660`, `63ca603` (later partial-revert), `41f9823`, `6a4b64d`, `4e289ba`, `bb82934`.

---

## TL;DR

`v0.2.0`'s `./install.sh` failed on any host that satisfies three conditions at once:

1. **MikroTik firewall** (or any firewall that proxies DNS over UDP but rejects DNS-over-TCP);
2. **≤10 GB of disk**;
3. **Docker bind-mounts `./data`** from a directory created by a previous root-owned process.

The fix did not require a code change in any single commit — it required 9 commits that, together, isolate and defang each failure mode. The release is verified end-to-end on a 5 GB-class VM behind a MikroTik (`192.168.88.2`), with both `recon-backend` (port 8000) and `recon-frontend` (port 8080) reporting `Up/healthy`.

If you hit any of these problems on your own host, jump to **[§6 Replicated install commands](#6-replicated-install-commands)** for the full sequence that works today. If you want to understand *why* each fix was needed, read top-to-bottom.

## 2. Diagnosis timeline (UTC, 2026-10-13/14)

### 22:00 — `v0.2.0` install attempt #1 fails
`./install.sh` reaches backend build, fails at `RUN go install subfinder...` with `lookup proxy.golang.org: no such host`. Host `nslookup proxy.golang.org` works (UDP DNS via MikroTik 192.168.88.2 → 142.250.218.209). Conclusion: Go resolver is failing on something `nslookup` doesn't.

### 23:10 — Hypothesis: blocked TCP DNS
`dig +tcp proxy.golang.org @192.168.88.2` → `connection refused`. **Confirmed**: MikroTik proxies UDP DNS but rejects TCP. Go 1.20+ pure-Go resolver falls back to TCP and fails with the confusing `no such host`.

### 23:30 — Tried several in-container DNS workarounds (all failed)
- `cf8b8e7` — `RUN echo "nameserver 1.1.1.1" > /etc/resolv.conf` in Dockerfile. **Failed**: BuildKit marks `/etc/resolv.conf` read-only.
- `cf8b8e7` — `--driver-opt dns=1.1.1.1` on `buildx create`. **Failed**: `docker-container` driver does not accept `--driver-opt dns` (only `network=`, `image=`, etc.).
- `cf8b8e7` — `--driver-opt config=...` for buildkit. **Failed**: same.

### 23:55 — Fix lives on the VM host, not in the build
`/etc/docker/daemon.json` with `{"dns": ["1.1.1.1", "8.8.8.8"]}` + `sudo systemctl restart docker`. Requires sudo (one-time). User provided password via chat. **Verified**: `docker run --rm alpine nslookup proxy.golang.org` now returns Google IPs (not MikroTik IPs). DNS root cause closed. (`ffba2df` reverts `cf8b8e7` since the in-build approach does not work.)

### 00:30 — Next layer: curl timeout
Backend build now passes DNS but fails at `curl https://go.dev/dl/go1.22.1.linux-arm64.tar.gz` with `Connection timed out after 300354 milliseconds` (= `--connect-timeout` default). `wget` from VM completes same download in 63s. **`f0d0660`**: add `--connect-timeout 600 --max-time 1800 --retry 5 --retry-delay 10 --retry-all-errors` to that curl.

### 01:30 — Next layer: install.sh non-TTY crash
Background install (`nohup ./install.sh </dev/null &`) dies at first `section()` call with `line 54: NC: unbound variable`. `install.sh:18` sets `set -euo pipefail`; `install.sh:47` else-branch (non-TTY) forgets to set `NC`. **`514ad72`**: add `NC=''` to the non-TTY branch.

### 02:00 — Next layer: disk exhaustion
Two parallel image builds (`recon-backend` + `recon-frontend`) on 1.7 GB free fill disk mid-`go install subfinder` with `mkdir /home/recon/tmp/go-build*: no space left on device`. Three attempts:
- **`63ca603`**: `--mount=type=tmpfs,target=/home/recon/.cache` and `/home/recon/tmp`, plus `--mount=type=cache,target=/home/recon/go/pkg/mod`. **Failed**: tmpfs/cache mounts default `root:root 0755`; `USER recon` then fails with `permission denied` (next row).
- **`41f9823`**: drop the `--mount=type=cache` (only that one; tmpfs stayed). **Still failed**: tmpfs at `/home/recon/.cache` still root-owned, recon can't write.
- **`6a4b64d`**: drop ALL `--mount=...` directives from the `go install` step. Keep `GOCACHE=/home/recon/.cache/go-build` and `TMPDIR=/home/recon/tmp` on real disk. **`4e289ba`**: replace `rm -rf /home/recon/{.cache/go-build,tmp,go/pkg/mod}` (permission denied because Go creates read-only files) with `go clean -cache && go clean -modcache` — Go's own tools handle permission tweaks before deletion.

### 03:00 — Container starts but stays Restarting(3)
`go install` succeeds. `docker compose up` creates the containers. But `recon-backend-1` reports `Restarting (3)` and `unhealthy`. Logs: `sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) unable to open database file`. **`bb82934`**: `chmod 777 ./data` in `install.sh` (line 547) before `docker compose up`. Verified: `curl localhost:8000/health` → `{"status":"ok","version":"0.2.1"}`. Frontend also `Up`.

### 03:25 — Tag `v0.2.1` pushed
`git tag -a v0.2.1 -m "..." && git push origin v0.2.1`. Repository and tag are clean on `bb82934`. Health endpoint serves the new version string.

## 3. Root cause analyses

### 3.1 MikroTik firewall TCP-DNS block

**Symptom**
```
go: github.com/projectdiscovery/subfinder/v2/cmd/subfinder@v2.6.3: lookup proxy.golang.org: no such host
```
even though `nslookup proxy.golang.org` returns an IP.

**Why**
- MikroTik's DNS proxy (`192.168.88.2`) answers UDP DNS queries normally.
- MikroTik's DNS proxy **rejects** TCP DNS queries (used for large answers, AXFR, and protocol fallbacks).
- Go 1.20+ ships a pure-Go resolver (`netgo`). For names that don't fit in a single UDP packet (e.g. large CNAME chains for `proxy.golang.org`), it retries over TCP. The retry fails with TCP RST; the resolver surfaces it as `no such host`, which is misleading.

**Diagnostic commands** (use these on any new firewall)

```bash
# UDP works:
nslookup proxy.golang.org 192.168.88.2

# TCP fails:
dig +tcp proxy.golang.org @192.168.88.2
# → connection refused
```

**Fix**
```bash
# On the VM host, write /etc/docker/daemon.json (requires sudo):
sudo tee /etc/docker/daemon.json > /dev/null <<'JSON'
{ "dns": ["1.1.1.1", "8.8.8.8"] }
JSON

sudo systemctl restart docker
```

Then verify from a container:
```bash
docker run --rm alpine sh -c "nslookup proxy.golang.org 2>&1 | tail -4"
# Should return Cloudflare/Google IPs, not your router's IPs.
```

**Why the fix lives on the host, not in the build**
- Dockerfile `RUN echo nameserver ... > /etc/resolv.conf` fails — BuildKit mounts `/etc/resolv.conf` read-only.
- `docker buildx create --driver-opt dns=...` fails — `docker-container` driver doesn't accept `--driver-opt dns`.
- The daemon-level DNS is the only knob that propagates to *every* container.

### 3.2 curl connect-timeout vs MikroTik TCP handshake to `go.dev`

**Symptom**
```
#20 393.8 curl: (28) Connection timed out after 300354 milliseconds
```

**Why**
- curl's default `--connect-timeout` is 300 seconds (5 minutes).
- MikroTik's TCP handshake to certain large CDN frontends (here: `go.dev`) exceeds 5 minutes on first hit (likely first-time SYN-handshake inspection or rate-limit accounting).
- `wget` has no separate connect-timeout, so it keeps retrying until `--timeout=600` elapses. It succeeded in 63 seconds the first time.

**Diagnostic command**
```bash
time wget --timeout=600 -qO /tmp/go.tar.gz https://go.dev/dl/go1.22.1.linux-arm64.tar.gz
ls -la /tmp/go.tar.gz
```

**Fix** (`backend/Dockerfile:59`)
```dockerfile
curl -fsSL --connect-timeout 600 --max-time 1800 --retry 5 --retry-delay 10 --retry-all-errors \
    "https://go.dev/dl/go${GO_VERSION}.linux-${go_arch}.tar.gz" -o go.tar.gz
```

**Generalization**
Any Dockerfile `RUN curl -fsSL https://...` that builds behind a corporate/state firewall should pass `--connect-timeout` ≥ 600 and `--retry` ≥ 3 with `--retry-all-errors`. The default 300s assumes an open internet.

### 3.3 install.sh non-TTY NC unset

**Symptom**
```
./install.sh: line 54: NC: unbound variable
```

at the first `section()` call, even though the script *worked* when run interactively from a real terminal.

**Why**
```bash
# install.sh:38-48
if [ -t 1 ]; then
  RED=... GREEN=... YELLOW=... BLUE=... CYAN=... BOLD=... NC='\033[0m'
else
  RED='' GREEN='' YELLOW='' BLUE='' CYAN='' BOLD=''
                                          # ← NC missing here
fi
# install.sh:50-54 uses ${NC}
log()    { printf "${BLUE}>>>${NC} %s\n" "$*"; }
```
When `[ -t 1 ]` is false (e.g., SSH without `-tt`, or `nohup ... </dev/null`), the else branch runs without setting `NC`. `set -u` at `install.sh:18` then aborts on `${NC}`.

**Trigger conditions** (any of these)
- `nohup ./install.sh </dev/null &` from an SSH session
- `./install.sh | tee log`
- Running inside `script(1)` without TTY emulation
- Running in any CI/CD runner that doesn't allocate a PTY

**Fix** (`514ad72`)
```diff
-  RED='' GREEN='' YELLOW='' BLUE='' CYAN='' BOLD=''
+  RED='' GREEN='' YELLOW='' BLUE='' CYAN='' BOLD='' NC=''
```

### 3.4 Disk exhaustion during build

**Symptom**
```
internal/profile: mkdir /home/recon/tmp/go-build2086379395/b764/: no space left on device
```
inside `RUN go install subfinder...`, after about 60 seconds of compilation.

**Why**
- `subfinder` is large (~600 MB of Go build artifacts across all its modules).
- `katana` is similarly large.
- The Dockerfile stages both `backend` and `frontend` images in **parallel** (Docker Compose `bake`).
- Each `RUN` step is a persistent layer; intermediate GOCACHE + TMPDIR content adds to layer size if not cleaned within the same `RUN`.
- a336b27 had moved GOCACHE and TMPDIR to `/home/recon/...` (out of `/tmp` tmpfs, which was too small at 2.6 GB). But files still ended up in the persistent layer.

**Diagnostic**
```bash
df -h /
# 1.7G free is too tight for two parallel builds.
docker system df
# Reclaimable build cache is what fills the rest.
```

**Fix** (`6a4b64d` + `4e289ba`) — keep GOCACHE/TMPDIR on real disk, but `go clean` at the end of the `go install` `RUN`:
```dockerfile
USER recon
RUN go install -v github.com/projectdiscovery/subfinder/v2/cmd/subfinder@v2.6.3 \
    && go install -v github.com/projectdiscovery/httpx/cmd/httpx@v1.3.7 \
    && go install github.com/tomnomnom/waybackurls@v0.1.0 \
    && go install -v github.com/projectdiscovery/katana/cmd/katana@latest \
    && go clean -cache && go clean -modcache
USER root
```
`go clean -cache -modcache` removes GOCACHE + module cache after install, in the *same RUN*. The committed layer state is just `/home/recon/go/bin/{subfinder,httpx,waybackurls,katana}`.

### 3.5 BuildKit mount UID mismatch (the regression that 63ca603 caused)

**Symptom** (introduced by `63ca603`)
```
go: failed to initialize build cache at /home/recon/.cache/go-build: mkdir /home/recon/.cache/go-build: permission denied
```

**Why**
- BuildKit's `--mount=type=tmpfs,target=/home/recon/.cache` creates the target as `root:root mode 0755` (no UID option for tmpfs).
- The next `USER recon` then can't write there.
- The same applies to `--mount=type=cache` (root-owned cache dir).

**Diagnostic** (catch this BEFORE re-running)
```bash
# After each build: check the log for "permission denied" combined with "go: writing stat cache"
grep -E "permission denied|stat cache" /tmp/recon-final-install.log
```

**Fix** (`6a4b64d`) — drop the `--mount` directives entirely; rely on `go clean` instead (see §3.4).

**Generalization** (warning to future maintainers)
- BuildKit `--mount` directives are non-trivial to get right across UIDs.
- If you need tmpfs in a Dockerfile, prefer a `USER root` block that creates the directory and `chmod`s it before `USER recon`.
- Or use a `--mount=type=cache,uid=...,gid=...` form (BuildKit ≥ 0.10) when available.

### 3.6 Docker bind-mount preserves host ownership

**Symptom**
```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) unable to open database file
ERROR: Application startup failed. Exiting.
Container recon-backend-1 Restarting (3) ...
```
even though `recon.db` writes *succeed* at first glance.

**Why**
- `docker-compose.yml:29`: `./data:/app/data` (bind-mount).
- Bind mounts **preserve the host's ownership** for the *contents* of the mount — they do not chown the inside.
- Container user `recon` is created with `useradd -r`, getting UID 999 (low system-UID range on Debian/Ubuntu).
- Host user `zimlama` is UID 1000 (typical first-user).
- On a fresh VM, `./data` is created by Docker itself (during volume prep or first bind-mount activation) as `root:root mode 0755` — *even when running docker rootless*.
- Inside the container, `/app/data` is therefore `root:root 0755`, and UID 999 can't write to it.

**Diagnostic**
```bash
ls -ld ~/recon/data              # on the host
touch ~/recon/data/test_write    # fails with "Permission denied"?
docker run --rm -u nobody recon-backend sh -c "ls -la /app/data"
```

**Fix** (`bb82934`) — `install.sh:547` chmods the dir before `compose up`:
```bash
chmod 777 ./data 2>/dev/null || warn "Could not chmod 777 ./data (non-fatal — runtime will surface the error if it matters)"
```
`chmod 777` is overkill but portable: it works regardless of host UID, rootless Docker, or user-namespace remapping. The dir contains only SQLite DBs and recon artifacts (no secrets), so 777 has no practical security downside.

**Alternative fix** (not adopted — left here for reference)
- In `docker-compose.yml`, add `user: "${RECON_UID:-999}:${RECON_GID:-999}"` and detect the host UID in `install.sh`. More complex; not worth it for a single-user app.

## 4. Prevention (what `install.sh` now does)

`install.sh:547` adds one line before `docker compose up`:
```bash
chmod 777 ./data
```

For new installs on a fresh host, the daemon-level DNS step (§3.1) is the **only** part that requires manual `sudo` outside `install.sh`. Consider adding it to `install.sh` in a future release — but doing so transparently requires the operator to type their sudo password into the installer.

The other four classes of failure (curl timeout, install.sh non-TTY, GOCACHE disk pressure, BuildKit mounts) are fixed permanently in v0.2.1.

## 5. What still requires manual intervention

- **Daemon-level DNS** (§3.1): one-time, VM host, requires `sudo`. Manual today.
- **5 GB-class hosts**: v0.2.1 builds work on 5 GB free disk but a fresh build takes ~10 minutes. Tighten to 3 GB and pip might fail; tighten to 2 GB and you need the cache-mount + `go clean` patterns from §3.5.
- **`./data` permissions after any direct container manipulation**: if a user shells into a container as root and writes into `/app/data`, the host bind-mount picks up root ownership again. Re-run `chmod 777 ./data` on the host.

## 6. Replicated install commands (works today)

These are the commands that produced a healthy v0.2.1 on armubuntu. Run them on the host as `zimlama` (or any user in the `docker` group). One line in the middle requires sudo.

```bash
# 1. (One-time, requires sudo) — DNS root cause fix
echo "$SUDO_PASS" | sudo -S bash <<'EOF'
cat > /etc/docker/daemon.json <<JSON
{ "dns": ["1.1.1.1", "8.8.8.8"] }
JSON
systemctl restart docker
EOF

# 2. Verify DNS from a container (should NOT show MikroTik IPs)
docker run --rm alpine sh -c "nslookup proxy.golang.org 2>&1 | tail -4"

# 3. Free up build disk space (clean any prior failed build)
docker system prune -af --volumes
docker builder prune -af

# 4. Pull and install
cd ~/recon
git pull --ff-only
chmod 777 ./data    # safe even if dir is empty/missing (will be created)
./install.sh        # ~12 minutes for first build + start

# 5. Verify
docker compose --profile prod ps
# Expect both containers Up. recon-backend should be "(healthy)".

curl -fsS http://localhost:8000/health
# Expect: {"status":"ok","version":"0.2.1"}
```

If `./install.sh` fails, capture the log and walk down `§1` in order: network → curl → disk → permissions → runtime. Each row of that table has the verbatim error message and the fix.

## 7. Lessons

For the **recon** repo:

1. **Default `--connect-timeout` is short.** Anywhere we put a `RUN curl -fsSL https://...` in a Dockerfile, we should add `--connect-timeout 600 --max-time 1800 --retry 3 --retry-all-errors`. Cheap insurance against corporate-network TIMEOUTS.
2. **`set -euo pipefail` is unforgiving.** All env vars referenced in a function need explicit defaults in every assignment branch. Add a lint for unset-VAR references early.
3. **BuildKit mounts are root-owned.** Don't combine `--mount=type={tmpfs,cache}` with `USER recon` without testing the UID flow explicitly.
4. **Bind-mount ownership = host ownership.** `chmod 777` the data dir before `compose up`. Or move to a named volume (no ownership mystery).

For the **AI workflow** that wrote this:

5. **Diagnose in dependency order.** When symptoms stack, fix the deepest layer first (DNS) and re-test. Don't try to apply every heuristic in parallel — it generates noise.
6. **Verify symptoms by running the actual failing component in isolation.** `curl` vs `wget` showed the timeout-vs-no-timeout split. `dig +tcp` vs `nslookup` showed UDP-vs-TCP DNS. Micro-benchmarks beat speculation.
7. **Tag only after end-to-end health verification.** Two `install.sh` runs ago I tagged prematurely (pre-compact summary). The `restart loop` from `./data` ownership only showed up *after* the build succeeded. `curl localhost:8000/health` is the only trustworthy signal.
